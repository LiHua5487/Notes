
# 网络应用的基本工作模型

## 进程与 Socket

一台设备里可能运行着很多程序，称为**进程（Process）**，把数据送到正确的设备里还不够，还必须交给正确的程序，这时候就需要两个概念
- **IP 地址**：用来定位网络中的一台主机或网络接口
- **端口号（Port）**：用来区分主机上不同的网络通信服务，其中 0～1023 称为熟知端口号，通常用于标准网络服务

比如一个 Web 服务器使用 `192.0.2.10` 这个 IP 地址，并在 `80` 端口提供 HTTP 服务，那么本地电脑上的浏览器就可以向 `192.0.2.10:80` 发出请求

那程序怎么收发数据呢？应用程序本身不需要知道数据实际经过了多少台路由器，也不必亲自控制网络信号，它只需要利用本机提供的通信接口 **Socket（套接字）**，把数据交给底下的传输层进行发送与接收

>IP 决定找哪台主机，Port 决定找哪个服务入口，是逻辑层面的；而 Socket 则是程序实际用来收发数据的通信对象，由本机的操作系统提供

可见网络应用层使得开发者可以不用关注传输层等底层细节，极大简化了网络应用开发

## TCP 与 UDP

现在浏览器已经知道怎么把数据交给网络了，但不同的应用，对网络运输的要求不一样：假如你要通过网络转账，数据当然必须准确到达；如果你正在和朋友语音通话，偶尔丢失极短的一段声音，可能只是稍微卡一下，反倒是声音延迟十秒钟才传来，更令人难以接受

传输层提供 TCP 和 UDP 两种协议给应用层，这里只需简单了解
- **UDP（用户数据报协议）**：最低限度的传输服务，无连接，不保证可靠性，但是机制简单、开销更小
- **TCP（传输控制协议）**：面向连接，提供可靠、有序的数据传输，丢失的数据可以重传，保证信息完整

## 应用程序的通信架构

**客户/服务器（C/S, Client/Server）架构**：客户端请求资源，服务器根据请求提供相应结果
- 可以按面向连接（TCP）与无连接（UDP）的方式分类
	- 对于使用 TCP 的服务器，存在两种 Socket ：监听 Socket 专门等待新的客户端来建立连接，连接 Socket 用来与客户端实际交换数据
- 也可以按服务器的实现方式分类
	- **循环方式**：一次只运行一个服务进程，按客户端请求的先后顺序处理，存在阻塞
	- **并发方式**：同时运行多个服务进程  ，每一个服务进程都对某个特定的客户进程做出响应

**P2P 架构**：C/S 模式下，客户端主要从服务器获取服务，但在 P2P 系统里，一个参与者既可以请求其他参与者的数据，也可以提供自己的数据，同时作为客户端和服务端

## 应用层协议

上一章已经介绍过，协议规定消息的格式、含义以及通信时需要遵守的处理规则，对应用层来说，这些规则可以非常具体：比如网页浏览有 HTTP，电子邮件传送有 SMTP，域名查询有 DNS 

# Web 基本概念

## 万维网与网页

浏览器上有各种视频网站、搜索网站或者学习平台，这些网站共同构成了我们熟悉的**万维网（World Wide Web，WWW）**，万维网不是互联网的另一个名字，而是建立在互联网上的一套资源组织、访问与展示体系；互联网是底层相互连接的网络系统，除了 Web，还能支持邮件、远程登录、文件传输、网络游戏等大量应用

万维网的一个核心思想，是让不同的资源能够彼此关联：比如一个网页上有着可以点击的链接，点击链接就跳转能访问其他图片、视频等资源，这类链接叫做**超链接（Hyperlink）**，而能够包含链接的文本称为**超文本（Hypertext）**

那浏览器显示的一个网页究竟是什么？服务器不是把一张完整的“网页截图”传给了你，而是会发送一份描述网页内容和结构的数据，浏览器再根据这些内容进行显示，最典型的就是 HTML（HyperText Markup Language，超文本标记语言）

除了 HTML，浏览器还可能获取 CSS（控制样式）、JavaScript（动态脚本）以及字体、视频等文件，这些能够被请求和传输的内容，统称为 **Web 对象**

## URL

浏览器不能只告诉服务器“我要网页”，必须有一种方法，准确地描述要访问哪个资源，这就是 **URL（Uniform Resource Locator，统一资源定位符）**，比如 `https://www.example.com:443/news/today.html` ，它由以下部分组成
- `https`：使用的访问方案
- `www.example.com`：目标主机的名称
- `443`：服务端口（使用默认端口时，通常不需要写出来）
- `/news/today.html`：要访问的资源路径

URL 还可以包含查询参数，比如 `https://www.example.com/search?q=network&page=2` 
- 参数部分以 `?` 开头，`&` 分隔不同参数
- 每个参数形如 `name=value` 

# 域名系统 DNS

## 域名

URL 中包含 `www.example.com` 这样的主机名，但是网络中是使用 IP 地址来寻址的，需要一套系统，可以根据名字找到对应的 IP 地址，这套系统就叫做 **DNS（Domain Name System，域名系统）**，而 `www.example.com` 这种名字就是**域名（主机名）**

>URL 中也不是必须包含域名，可以把域名直接替换为 IP ，比如 `http://192.168.1.1/admin` 

域名与 IP 并不是一一对应的关系，一个域名可能对应多个 IP ，将不同的用户分配到不同的服务器，降低负载；多个域名也可能对应同一 IP ；一个域名的 IP 也可能发生变化，比如服务器维护，改变 IP 暂时用另一个服务器

由于 IP 地址和域名实在太多了，不方便直接记录成一个大表格，所以 DNS 采用层次化、分布式管理的设计
- 层次化：域名按树状结构组织 **（域树）**，服务器按照域名的层级分工，各自负责一部分工作
- 分布式：信息分散保存在不同的服务器上，不要求一台机器保存所有信息

比如 `www.pku.edu.cn`，从右往左看
- `.cn` 是**顶级域名（TDL，Top Level Domain）**，表示中国国家顶级域名
- `edu.cn` 是其中与教育有关的域名空间
- `pku.edu.cn` 是北大使用的域名
- `www.pku.edu.cn` 则是进一步划分出来的名称

## 域名服务器

假设我们要查询 `y.abc.com` 的 IP 地址，DNS 不是让所有服务器都保存这条记录，而是让不同层级的服务器各司其职，每台服务器保存域树的数据，以及相邻域名服务器的信息（自身信息缺失时，向谁查询）

![[计网/imgs/img2/image.png]]

- **根名字服务器（Root Name Server）**：并不保存每个网站的 IP 地址，而是帮助查询者找到相关顶级域名的信息
- **顶级域名服务器（TLD Name Server）**：负责相应顶级域名下的委派信息，例如查询 `abc.com` 时，`.com` 服务器可以告诉查询方负责 `abc.com` 的权威域名服务器在哪里
- **二级/权威域名服务器（Authoritative Name Server）**：负责某个 DNS 管理区域的权威记录（“权威”可以简单理解为：它是相应域名区域正式信息的提供者）
- **本地域名服务器（递归解析器）**：通常由互联网服务提供商、学校、企业或其他服务机构部署，距离用户较近

这里还有一个容易混淆的概念：域和区（zone）
- **域（domain）**：域树中的一个命名范围，即一个子树
- **区（zone）**：每一个主机都必须在某个二级域名服务器处注册登记，各个二级域名管理机构又把所属域名划为若干个部分，分别由不同服务器管理，是实际的管理单位

![[计网/imgs/img2/image-3.png]]

## DNS 的查询过程

DNS 查找域名对应的 IP 时，包含以下两种查询方式
- **递归查询**：当收到请求的域名服务器不知道对应的 IP 时，该域名服务器替请求者继续查询（一般在本地服务器内部采用）
- **迭代查询**：当收到请求的域名服务器不知道对应的 IP 时，把自己知道的下一跳地址告诉请求者，由请求者自己继续向该域名服务器查询（通常本地DNS之上使用）

![[计网/imgs/img2/image-1.png]]

在实际查询时，通常是两种方法结合

![[计网/imgs/img2/image-2.png]]

**缓存机制**：在查询时，电脑或本地 DNS 服务器中可能有之前查询结果的缓存，如果缓存仍在有效期，就直接返回结果，称为**缓存命中**

比如学校里的同学刚刚访问过某个网站，学校的 DNS 解析器已经保存了该域名的 IP 地址，你随后访问同一个网站时，它可能直接把缓存里的结果返回给你，不必再从根服务器开始查询

## DNS 报文

DNS 服务器之间交换的信息有固定的格式，在传输层通常使用 UDP 协议，默认端口号为 53，报文类型分为**查询请求（query）** 和**查询响应（reply）** 两类，它们的结构差不多，主要由以下的部分组成
- **基础结构（首部）**：说明这是什么报文、查询与响应的状态、各部分分别有多少条记录
- **问题部分**：说明查询的名称、信息类型和查询类别
- **资源记录部分**：可以包含回答、权威名称服务器信息和附加信息，**通常只出现在响应中**

![[计网/imgs/img2/image-4.png]]

## DNS 缓存、TTL 与安全性

如果每次访问网站都从根服务器开始逐级查询，不仅增加等待时间，也会给 DNS 系统带来额外负担，所以电脑、本地解析器以及其他 DNS 服务器都可能缓存已经获得的信息，但这里有一个问题：如果网站的 IP 地址变了，缓存中旧的地址怎么办？

这就需要 **TTL（Time To Live，生存时间）**：TTL 以秒为单位，表示一条资源记录可以被缓存使用多长时间，过期后就失效了，如果还需要该信息，就得重新获取
- TTL 较长：重复查询较少，缓存利用率高，但信息变化后，旧缓存可能保留更久
- TTL 较短：缓存更新得更及时，但查询请求可能更多

此外，DNS 还存在安全性问题，传统 DNS 在设计之初没有充分考虑安全问题，常见问题包括
- 查询内容可能暴露用户访问了哪些域名
- DNS 记录如果没有得到有效验证，查询方可能收到伪造或被篡改的结果
- DNS 使用缓存后，如果缓存中的信息不正确，也可能影响后续查询

DNSSEC 使用数字签名来进行验证：域名服务器对资源记录签名，验证方使用相应的公开密钥验证签名，其核心是验证 DNS 数据的真实性和完整性，而不是加密用户的查询内容

# HTTP

有了 DNS ，我们终于知道目标服务器的 IP 了，接下来需要传输“我想获取什么资源”的信息，这就需要 **HTTP（HyperText Transfer Protocol，超文本传输协议）**，它规定了 Web 客户端与服务器怎样交换请求和响应，在传输层通常使用 TCP 协议，默认端口号为 80

HTTP 在发展过程中产生了很多个版本，比如 HTTP/1.1、HTTP/2、HTTP/3，规定了 HTTP 数据如何组织、编码和传输

HTTPS 则引入了 TLS 加密技术，注意 HTTPS 并不是 HTTP 的一个版本号，而是决定 HTTP 传输时是否进行加密，对应 `http://` 与 `https://` ，HTTPS 的默认端口号为 443 

## HTTP 请求报文

HTTP 的请求报文由以下三部分组成
- **开始行（请求行）**：包含请求方法、请求资源的 URL（相对主机的路径）、HTTP 协议版本，说明要对什么资源执行什么操作
- **首部行**：包含主机地址、数据类型、身份认证等附加信息，说明请求的相关属性和要求
- **实体主体**：包含客户端发送给服务器的具体数据，即请求实际携带的内容，可以为空

![[计网/imgs/img2/image-5.png]]

开始行的方法部分，有两个很常用的方法
- **GET**：读取 URL 的资源
- **POST**：向 URL 提交数据，让服务器处理

比如想要在 `https://example.com/register` 注册账号，先获取网页资源

```http
GET /register HTTP/1.1
Host: example.com
Accept: text/html
```

其中第一行为请求行

```
GET /register HTTP/1.1
``` 

之后的两行为首部行，实体主体为空

```
Host: example.com
Accept: text/html
```

- `Host`：主机域名
- `Accept`：期望接收到的信息的格式

而后发送账号信息

```http
POST /register HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 43

{"username":"zhangsan","password":"123456"}
```

首部行为

```
Host: example.com
Content-Type: application/json
Content-Length: 43
```

- `Content-Type`：实体主体的数据的类型
- `Content-Length`：实体主体的长度

实体主体和前面中间用一个空行隔开，包含提交的数据

```
{"username":"zhangsan","password":"123456"}
```

POST 其实也可以用来获取资源，只不过和 GET 在参数位置上不同，比如要从 `https://example.com/search?keyword=computer&page=1` 获取资源，分别用 GET 和 POST 的写法

```http
GET /search?keyword=computer&page=1 HTTP/1.1
Host: example.com
Accept: text/html
```

```http
POST /search HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 23

keyword=computer&page=1
```

其中 POST 相当于给服务器提交了一次表单请求，本质上和 GET 干的事一样

## HTTP 响应报文

HTTP 响应报文的结构和请求报文类似，但是包含的信息不同，开始行在此又称**状态行**

![[计网/imgs/img2/image-6.png]]

其中**状态码（Status Code）** 表示请求的处理情况，比如
- `1xx`：通知信息，比如已收到请求/正在处理
- `2xx`：请求成功，比如 `200 OK` 
- `3xx`：重定向，需要进一步处理
- `4xx`：客户端请求方面的错误，比如 `400 Bad Request` （无法解释请求报文）、`404 Not Found` （服务器找不到请求的资源）
- `5xx`：服务端处理方面的错误，比如 `500 Internal Server Error` 

前面使用请求报文获取网页，对应的一个响应报文可能长这样

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 45

<html>
  <body>Hello!</body>
</html>
```

## HTTP 的版本发展

早期的 HTTP/1.0 版本采用**非持久连接**：每获取一个对象，就建立一次 TCP 连接，用完后立刻关闭，多次获取就得反复开关

HTTP/1.1 默认支持**持久连接**：建立一次 TCP 连接后，不要每获取一个对象就立即关闭，而是可以继续在这条连接上发送后续请求

HTTP/1.1 除了保持连接，还引入了**流水线（Pipelining）**，可以不用等前一个请求的响应到达，就发出下一个请求

![[计网/imgs/img2/image-7.png]]

但是 HTTP/1.1 流水线要求响应按照请求顺序返回，如果 A 处理很慢，B 即使先准备好了，也会受到阻碍

HTTP/2 为此引入了**多路复用**，让多个请求和响应的数据片段交错传输，此外还加入了二进制报文格式、首部压缩等机制

不过，HTTP/2 底层仍使用 TCP，所以 TCP 某些丢包造成的等待问题仍可能影响多个 HTTP 数据流

HTTP/3 则更进一步，它不再依赖 TCP，而是使用建立在 UDP 之上的 QUIC 协议，由 QUIC 实现可靠传输、安全保护和多路传输等功能

## HTTP 的无状态特性

**无状态协议**：服务器端不保留之前请求的状态信息 ，效率低，但简单  
**有状态协议**：维护状态相对复杂，需要维护历史信息，在客户端或服务器出现故障时，需要保持状态的一致性等

>有/无状态：是否需要记住之前的通信信息；面向连接/无连接：通信前是否需要建立连接

HTTP 是无状态协议， 比如先后发出“打开首页”和“打开购物车”的请求，HTTP 协议本身并不要求服务器记住之前的请求内容，也不要求记住“这次请求和刚才的首页请求来自同一个用户”

尽管 HTTP 本身是无状态的，但网站可以在 HTTP 之上利用 Cookie、数据库等机制实现有状态的用户体验

## Web 缓存

Web 缓存主要存在两个地方
- **浏览器缓存**：保存在用户设备中
- **代理服务器缓存**：多个用户的 HTTP 请求可能先经过中间的一个代理服务器，再转发给原始服务器，代理缓存能让多个用户复用某些资源

引入缓存能减少访问远方服务器的次数，也减少了接入链路上的负担，但是缓存的资源不一定是最新的，为此有以下解决办法
- 启发式缓存更新策略（服务器返回）：服务器响应包含 `Last-Modified` 和 `Expires` 字段，表示缓存信息的修改时间和有效期，但很难预测准确的有效期
- 询问式缓存更新策略（客户端发起）：客户端请求包含 `If-Modified-Since` 字段，表示“如果这个资源在指定时间之后修改过，请把新版本发给我”，如果资源没变化，服务器可以返回 `304 Not Modified` ，浏览器继续使用现有缓存；如果资源变化了，则可以返回 `200 OK` 并附带新资源

## Cookie 与安全

想象你刚刚登录了一个购物网站，你输入账号和密码，网站确认身份，然后把首页显示给你，接着你点击购物车，因为 HTTP 是无状态的，新的 HTTP 请求本身并不会天然继承刚才的登录信息，难道每点一次页面，都要重新输入密码？为了解决这种问题，Web 使用了 **Cookie**，运行过程如下
- 浏览器第一次访问网站时，服务器会在响应的首部行里使用  `Set-Cookie: SID=abc123` 进行唯一性标识，并以其为关键字存储相关会话
- 浏览器把 Cookie 保存在本地，并按其适用范围管理
- 浏览器后续的请求会在首部行附带上 `Cookie: SID=abc123` ，表明这个请求是之前请求的后续
- 服务器用 `abc123` 查找保存的会话信息，从而知道这个请求对应哪个会话

Cookie 很方便，但也有潜在风险：网站可以利用 Cookie 及其他技术记住用户偏好、关联访问行为，包括但不限于给你推广告，而且攻击者也可能偷到你的 Cookie 并冒用身份

现在很多 Web 访问通常会添加身份认证机制，当你访问一个需要认证的资源时，服务器在响应的首部行中包含 `WWW-Authenticate` 字段，表示该资源需要身份认证，浏览器随后可以发送包含 `Authorization` 字段的请求，携带用户名、密码等信息，让服务器验证凭据

# 电子邮件服务

电子邮件系统包含以下几个部分
- **用户代理（邮件客户端）**：用来编写、发送、读取和管理邮件的软件
- **传输代理（邮件服务器）**：负责接收、转发和保存邮件，服务器中有用户的邮箱，用来存放收到的邮件；还有邮件输出队列，用来保存等待发送或转交的邮件
- 传输协议：SMTP、POP3、IMAP 等

## 邮件格式与 MIME

邮件的基本格式
- 首部：描述邮件的相关信息，例如 `From:`、`To:`、`Date:`
- 主体：邮件的正文，与主体之间用一个空行分隔

基本的 ASCII 电子邮件使用 RFC 5322 格式，但是当我们希望在邮件里加入中文、图片、音频或者文件附件时，就需要使用 **MIME（Multipurpose Internet Mail Extensions，多用途 Internet 邮件扩展）** 格式，它扩展了邮件的描述方式，可以标明内容的类型、组织多部分消息，对其进行编码，邮件系统通过 MIME 相关信息识别这些内容应该如何解释和展示

## SMTP

首先，Alice 需要把邮件发送到 Bob 的邮件服务器，这个过程采用的协议是 **SMTP（Simple Mail Transfer Protocol，简单邮件传输协议）**，使用 TCP，默认端口号为 25，采用**推（Push）** 的方式，将邮件从发送方邮件服务器传送到接收方邮件服务器，而不需要接收方主动请求这封邮件，整个过程分为三个阶段：建立连接、传送邮件、关闭连接

SMTP 采用命令与响应的交互方式，客户端发送命令，服务器返回状态码和简短说明，它是一个简单的 ASCII 协议，邮件必须为 7 位 ASCII 

SMTP 的局限
- 本身不包含完整的认证机制
- 传输 ASCII 而不是二进制数据，还需要 MIME 等机制配合
- 邮件以明文形式出现，未经过加密，传输过程中可能暴露内容

## POP3、IMAP 与 Webmail

现在，Alice 已经发送成功，邮件也已经存放在 Bob 的邮件服务器中，接下来的问题是：Bob 怎么把邮件从服务器中读出来？这个过程使用 POP3、IMAP 等邮件访问协议，采用**拉（Pull）** 的方式，接收方主动向服务器请求查看或获取邮件

**POP3（Post Office Protocol Version 3，第三版邮局协议）**：使用 TCP，默认端口号为 110，采用 C/S 的工作方式，接收端用户的主机中需要运行 POP 客户端程序，其邮件服务器中需要运行 POP 服务端程序，包含以下过程
- 认证：用户通过用户名、密码等方式完成登录认证
- 事务处理：用户查看邮件列表、获取邮件，并可以将邮件标记为删除
- 更新：结束会话时，删掉被标记的邮件

**IMAP（Internet Message Access Protocol，互联网邮件访问协议）**：默认端口号为 143，是 POP3 的改进版本：POP3 只是把服务器上的邮件取到本地或删除，而 IMAP 还能直接管理服务器上的邮箱，比如已读未读、分文件夹，能在多个设备间同步邮件状态

**Webmail**：用户代理就是普通浏览器，浏览器与邮箱服务器之间通过 HTTP 等 Web 技术通信，而不需要安装邮件客户端
