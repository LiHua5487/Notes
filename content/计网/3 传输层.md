
# 传输层的基本概念

## 端口与 Socket

应用层约定好了要传递什么样的信息，之后便通过 Socket 把信息交给传输层进行传递，传输层负责两个主机中的进程与进程间的通信，而接下来的网络层则负责主机之间的通信，可能经过多跳链路进行数据传输
- 传输层：将快递从发送者手里取走，交给对应的接收者，并确认有没有丢件、顺序是否正确
- 网络层：责规划包裹经过哪些中转站

Socket 会在本地关联一个端口号（一个 Socket 通常只关联一个端口，但一个端口可以有多个 Socket 关联）
- 客户端通常由操作系统自动分配，创建 Socket 时不指定端口
- 服务端通常在创建 Socket 时关联到指定的端口

端口号长度为 16bit ，在传递的信息中，通常不能只包含目标进程的端口，还需要包含源端口，否则目标进程收到消息后不知道回复给谁

## TCP 与 UDP

**UDP（用户数据报协议）**
- 最低限度的传输服务，无连接，不保证可靠性，但是机制简单、开销更小
- 发送、接收数据的单位是报文，边界明确，提供报文检错功能，但是不会自动纠正、重传
- UDP 没有建立连接的延迟，也不限制发送速率（不进行拥塞控制和流量控制），适合容忍丢包但对延迟敏感的场合使用（如流媒体），或者以单次请求/响应为主的应用

**TCP（传输控制协议）**
- 面向连接，提供可靠、有序的数据传输，丢失的数据可以重传，保证信息完整，同时提供拥塞控制和流量控制
- 以字节流的形式收发数据，多个消息可能直接连在一起，边界不明确，接收方需要自己区分消息

## 复用与分用

当多个进程都需要传输数据时，操作系统不会为每个程序重新建设一套独立的底层网络，而是把各个 Socket 提供的数据交给共同的网络层，这个过程称为**复用（Multiplexing）**：发送端传输层从多个 Socket 收集数据，添加必要的传输层信息，比如 Socket 的标识，再交给网络层发送

当网络层收到数据时，传输层需要根据报文携带的信息判断该交给哪个 Socket，这个过程称为**分用（Demultiplexing）**：接收端传输层根据 Socket 标识，把收到的数据分配给正确的 Socket 

UDP 使用 `<本地IP，本地端口>` 来标识 Socket，接收方接到 UDP 报文后，`<目的IP，目的端口>` 相同的报文会被交给同一个 Socket，而报文段中的 `<源IP ，源端口>` 则被用来发送响应报文

TCP 则使用两种 Socket，将不同客户端的请求区分开
- **监听 Socket**：等待客户端的连接请求，该 Socket 具有众所周知的端口号
- **连接 Socket**：接到请求后，创建一个连接 Socket（仍使用监听端口号），使用 `<源IP ，源端口，目的IP，目的端口>` 进行标识，每个连接 Socket 只与一个客户通信，传输层据此将 TCP 报文交给对应的 Socket

# UDP

为什么说 UDP 不保证可靠性？其实网络层本身提供的服务就不保证可靠性，也不保证带宽和延迟要求，只是尽力将数据包交付给目标主机，而 UDP 只是对其进行最简单的封装
- 加入了针对 Socket 的复用和分用机制（必有），把网络层的主机到主机传输，变成进程到进程传输
- 也可能加入报文检错功能（可选），但不会主动纠错

## 报文结构与检错

实际上，数据的传输是经过多层封装的，应用层会根据自己的协议封装一遍交给传输层，传输层也会根据自己的协议再封装一遍，UDP 会在应用层给到的数据前面加一个 UDP 首部，把应用层数据作为 UDP 报文的**载荷（Payload）**

![[多模态学习/imgs/img1/image.png]]

源/目标端口、报文长度、校验和都是 16bit ，其中校验和的检错机制是这样的：报文本质也是一串 01 序列，发送方将报文看成由一系列 16bit 的整数相连组成的，对这些整数进行求和，接收方对收到的报文进行相同的计算，并与 checksum 字段比较，具体的计算过程为
- 发送方把报文按 16bit 为一组进行拆分，如果不够就在末尾补 0 
- 但是 checksum 字段本身只有 16bit ，求和结果可能超出这个范围，于是把溢出的进位加回末尾
- 将求出的 16 位和逐位取反，放入 checksum 字段，这一步的意义在于方便接收方校验，接收方只需要将自己的求和与 checksum 相加，如果没有出错，那结果的每一位应该都是 1 

实际上，计算校验和时还会在报文前面拼一个**伪头部（Pseudoheader）**，包含源 IP、目的 IP、协议号、UDP 长度，这样将 IP 信息也纳入了校验范围

![[多模态学习/imgs/img1/image-1.png]]

>伪头中协议号与UDP 长度一行可能不够 32bit ，需要在前面补 0 

checksum 也不是一定能检测出错误，比如两个 16 位整数在同一位发生 0-1 翻转，求和结果不变，此时需要应用层进一步识别并处理错误，但其仍被使用，因为
- 传输层出错概率很小，一般来源于软件 bug 或硬件故障
- 底下的链路层也有纠错功能，将大部分网络传输过程的错误处理了
- checksum 的计算开销小

## UDP 缓冲区

当 UDP 报文较多时，一部分会存入缓冲区，UDP 缓冲区通常由主机内部实现，而且只在接收时使用
- 发送：从应用层获取的数据，在传输层添加 UDP 头部后直接交给网络层，缓冲机制由底下的网络层、链路层提供
- 接收：每个 Socket 都有一个缓冲区，存储接收到的报文

# 可靠数据传输

**可靠数据传输（Reliable Data Transfer，RDT）**：无论底下的网络怎出错，交给上层应用程序的数据仍然正确、完整、有序
- 正确：数据内容不能被意外改变
- 完整：不能凭空少掉某部分数据
- 有序：接收方获得的数据顺序与发送方的顺序一致，而且不会重复交付

可靠传输不仅是 TCP 中的问题，在网络的各个层次都需要考虑，这里只考虑以下情况
- 不可靠信道：存在数据丢失、乱序，或发生随机错误（数据的某些位发生 0-1 翻转，但可被检测出来）
- 不考虑恶意篡改、第三方伪造数据等情况

可靠性机制是一种分布式算法，即发送方、接收方各自都应执行相应操作，协同保证可靠性，两方的功能可以用有限状态机（FSM）进行表示，可以简单理解成在不同情况下，应该做不同的事情

## 一般的可靠性方案

在设计可靠方案时，可以从简单到复杂逐步考虑：先假设完美情况，再假设如果发生出错、丢包时要怎么办，最后考虑性能优化、乱序处理

这个假设过程的不同阶段分别对应着 rdt 1.0、2.0、2.1、2.2、3.0 协议，它们不是 TCP 的正式版本，而是一系列教学模型
- rdt 1.0：完美信道
- rdt 2.x：有错但不丢包
- rdt 3.0：有错且丢包

先看 **rdt 1.0（乌托邦协议）**：信道根本不会出错，那协议就不用操心可靠性问题，发送方只需要拿到数据、打包发送，接收方只需要接收、取出数据、交给应用程序，双方不断进行这个循环就行了

进一步的，假设信道可能发生错误，但不会丢包，接收方就需要检错机制判断收到的数据是否出错，但是出错了咋纠正呢？一个自然的想法是：让发送方再发一遍正确版本，这套思想叫作**自动重传请求（ARQ，Automatic Repeat reQuest）**，可以进一步拆解成三部分
- 检错：接收方检测数据有没有出错
- 反馈：接收方根据检错结果，向发送方发出反馈
- 重传：发送方重新传输数据

**rdt 2.0** 就是一个最简单的 ARQ 协议
- 接收方的反馈有 **ACK（Acknowledgment）** 和 **NAK（Negative Acknowledgment）** 两种，表示收到消息且消息正确/出错，由于其只表示一种状态，具体内容没有意义，所以称为**哑帧（dummy frame）**
- 发送方发送一个数据包后暂停，等待反馈到达后才发送下一个包，这种需要停下来等待的协议称为**停等式协议**

但是问题在于，反馈的传输过程也可能出错，发送方如果收到出错的反馈，就无法判定接收方到底有没有收到正确的数据，如果直接重传，接收方就会收到两份数据，但是接收方并不能区分这是正常反馈后继续传来的新数据，还是因为反馈出错导致的重传数据，一些情况下很严重，比如其内容是「账户加 100 元」，如果接收应用把它执行两次，结果显然不对

**rdt 2.1** 给每个数据包添加一个**编号 Seq** ，来区分是不是新数据包，由于采用停等式协议，所以只需要让新数据包和前一个数据包的 Seq 值不同就行，因此 Seq 交替取 0/1 就足够了，重传时 Seq 不变，传输新数据时进行翻转

**rdt 2.2** 则**只用 ACK 一种反馈**，不用 NAK ，因为有了 Seq ，完全可以在 ACK 反馈中加上最近成功接收的数据包的 Seq，比如 ACK0、ACK1（由于是停等式协议，如果收到的数据包出错，那 Seq 就是上一个数据包的），如果发送方收到的 ACK 出错，或其中的 Seq 和当前的不同，就进行重传

现在把假设进一步扩展：可能出现丢包，不只是发送的数据包可能丢失，反馈也可能丢失，但是前面的 rdt 2.x 又是停等式协议，如果数据包丢失，接收方就不知道数据到底来没来，自然没法发送 ACK，即便收到数据包，反馈的 ACK 也可能丢失，那发送方就会一直等下去

**rdt 3.0** 引入了**超时重传**，搞一个计时器（Timer），设定一个等待期限，发送方发送数据包后启动计时器，如果超过规定时间仍然没有收到正确的 ACK，就重新发送

但是超时并不代表数据包一定丢失，也可能是因为网络拥堵等原因，这样仍然会产生重复数据，不过在 rdt 2.1 中已经使用 Seq 解决了重复问题，所以无所谓了

总结一下，rdt 3.0 集成了检错 + 自动重传 + 编号去重 + 超时重传，发送方和接收方的状态机如下
- 发送方
	- 准备数据，附加 Seq 序号和其它校验信息
	- 发送数据包，启动计时器并等待
	- 收到正确的 ACK：停止计时，发送下一包
	- ACK 损坏、不匹配或超时：重传
- 接收方
	- 收到正确且序号符合预期的数据：交付应用，发送 ACK，并更新 Seq 序号
	- 数据损坏或序号不符合预期：不向应用交付这份数据，并按照协议重新反馈确认

但是 rdt 3.0 仍然是停等式协议，信道利用率太低了：设数据包大小为 $F$ ，信道发送速率为 $R$ ，信道传播时延为 $I$ ，发送方需要 $F/R$ 的时间把数据包放到网络链路里，但是还需要 $RRT=2I$ 的时间才能收到反馈，大部分时间都在等待，信道利用率只有

$$
U = \frac{F/R}{RRT+F/R}
$$

## 性能优化

### 流水线传输

**流水线传输（Pipelining）**：发送方可以连续发送，假设每轮连续发送 $N$ 个包，则利用率近似为

$$
U = \frac{N\cdot F/R}{RRT+F/R}
$$

但是这引入了新的问题
- 序号 Seq 只有 0/1 不够用了，需要添加新的编号
- 发送方需要保存所有未被确认的数据包，不然一旦有其中一个丢失就没法弥补了
- 多个数据包可能分别丢失、损坏或乱序，要同时管理许多个包，复杂度大大增加，接收方处理速度可能跟不上发送速度
- 连续上传多个包会占用网络带宽

### 滑动窗口

为了限制开销，可以使用**滑动窗口**：限制发送方最多同时有 $N$ 个已经发送、尚未确认的数据包

![[多模态学习/imgs/img1/image-2.png]]

但是这里也有一个极端情况，由于序号一直滚动复用，当滚动到之前用过的序号时，可能没法区分一个数据包是新发的，还是经过很长时间后才重传过来的

![[多模态学习/imgs/img1/image-3.png]]

有了滑动窗口，发送方可以连续发送多个数据包，但新的问题来了，有时候不只需要保证数据包传到了，还需要保证顺序，但是发送顺序不一定就是接收顺序，假设发送方一次发送了 `pkt0、pkt1、pkt2、pkt3` ，结果 `pkt2` 丢了，但 `pkt3` 正常到达，接收方该怎么办？有以下两种应对办法：回退 N 、选择重传

### 回退 N 

**回退N算法（GBN，Go-Back-N）**：接收方只按预期顺序接收数据包，后面的提前到了直接扔掉

这样以来，接收方不用缓存乱序的数据包，只需要维护下一个期待的序号，但代价是可能会进行更多的重传

GBN 在反馈时，不会单独确认每一个数据包，而是使用**累积确认（Cumulative ACK）**：假设收到 `ACK3`，表示序号 0、1、2、3 的数据包已经全部被正确、连续地收到，这样发送方无需等待这四个包各自的确认，也可以减少由 ACK 丢失造成的重传（比如 `ACK2` 可能丢失，但正常收到 `ACK3`，就能得知前面的都正常了，不需要重传）

发送方维护两个变量
- `SendBase`：最早的、尚未确认的数据包序号
- `NextSeqNum`：下一个准备发送的数据包序号

设窗口大小为 N ，只要 NextSeqNum < SendBase+N ，就说明窗口里仍有可用位置，可以继续发送

GBN 还采用一种简单的定时器策略：只给最早未确认的数据包维护一个定时器，如果超时，就把从 `SendBase` 开始到当前已发送末尾之间的所有未确认数据包重新发送

但是仅仅因为前面一个包没到，就把后续的全扔了，还是不够高效

### 选择重传

**选择重传算法（SR，Selective Repeat）**：既然后面的数据包已经正确到达，就没必要丢掉，而是先缓存起来，等待前面缺失的数据包补齐后再按顺序交给上层应用

同时，SR 的反馈使用独立确认，比如 `ACK3` 只表示 pkt3 已收到；SR 的发送方一般还需要为各个未确认数据包分别计时，从而知道具体哪个包超时，超时了也只重传该数据包，这样虽然不用重传那么多次，节省了带宽，但发送方要管理更多定时器，接收方也要使用更多缓存空间

# TCP

TCP提供的服务
- 在一对进程间提供一条理想的字节流管道
- 点到点通信：仅涉及一对进程
- 全双工：允许双向传输
- 可靠、有序的字节流

需要的机制
- 建立连接：通信双方为本次通信建立数据传输所需的状态（Socket、缓存、变量等）
- 可靠数据传输：流水线式发送、报文检错、丢失重传
- 流量控制：发送方不会让接收方缓存溢出
- 拥塞控制：发送方不会造成网络拥塞

## TCP 的基本收发

与 UDP 不同，TCP 是面向字节流的：假设应用程序要发送一句话 `HELLOWORLD` ，TCP 看到的是连续的字节

```
H E L L O W O R L D
```

它会把这10个字节划分成一系列报文段来发送，比如 `HEL、LOW、ORL、D` ，或者 `HELLO、WORLD` 

在发送时，TCP 给字节编号，并记录报文段的起始序号与长度，接收方据此还原出字节序列

```
报文段1：Seq=100      报文段2：Seq=105
 H   E   L   L   O  |  W   O   R   L   D
100 101 102 103 104 | 105 106 107 108 109
```

此外，TCP 的反馈 ACK-n 的含义也不一样，表示接收方已按序收到前面的字节，**下一个期待收到的字节序号为 n** ，比如发送方发送了 100~120 的字节，接收方的反馈应该是 `ACK121` 

>报文段的 Seq 称为发送序号，ACK-n 中的数字 n 称为确认序号

发送端维护 `SendBase` 和 `NextSeqNum` 两个变量，假设把一段字节流拆成了以下报文段连续发送出去
- S1：Seq=100，长度 20 字节
- S2：Seq=120，长度 20 字节
- S3：Seq=140，长度 20 字节

此时 `SendBase=100`，`NextSeqNum=160` ，如果接收方返回 `ACK=140`，就说明 100～139 的字节已经连续收到，于是发送方可以将 `SendBase` 从 100 更新为 140 

TCP 的超时重传也和 GBN / SR 不同，**只对最早未确认的报文段使用一个重传定时器**，但发生超时时，通常只重传那一个报文段，并把提前收到的后续报文段缓存起来，不直接丢掉，也不需要给每次发送都设置计时器

之前还提到，TCP 是全双工的：A 给 B 发数据的同时，B 也可以给 A 发，如果 B 准备发送反馈时，正好也有数据要发给 A，就把 ACK 和 B 的数据的 Seq 一起发送，不必分成两次，这叫**捎带（piggyback）**

## TCP 的性能优化

### RTT 动态估计

超时重传的定时器到底应该设成多久？如果只等10毫秒，正常网络延迟可能比这还大，发送方就会不停地误判丢包；如果等10秒，虽然不容易误判，但真正丢包后又要等很久才能恢复

TCP 没有设置一个固定的时间，而是会不断测量 RTT，假设发送方在时刻 $t_1$ 发送了一个报文段，在时刻 $t_2$ 收到它的 ACK ，则一次 RTT 测量结果就是

$$
\text{SampleRTT}=t_2-t_1
$$

但如果直接把最近一次 SampleRTT 设为超时时间，会很不稳定，TCP 将当前测量与历史结果进行加权平滑，作为 RTT 的估计值

$$
\text{EstimatedRTT} = (1-\alpha)\cdot\text{EstimatedRTT} + \alpha\cdot\text{SampleRTT}
$$

### DevRTT与超时间隔

仅使用平均 RTT 仍然不够，设想两个网络：网络 A 的 RTT 一直在 98～102ms 之间，很稳定；网络 B 的 RTT 在 50～150ms 之间波动，虽然平均值也可能是 100ms ，但变化非常剧烈，显然网络 B 的超时值应该留出更大的余量，因此 TCP 还会估计 RTT 的波动幅度，称为 **DevRTT**

$$
\text{DevRTT} = (1-\beta)\cdot\text{DevRTT} + \beta\cdot\lvert \text{SampleRTT} - \text{EstimatedRTT}\rvert
$$

最后将超时间隔设为

$$
\text{TimeoutInterval} = \text{EstimatedRTT} + 4\cdot\text{DevRTT}
$$

### Karn 算法

但是在计算 RTT 时，又会有一个问题：假设发送方发出一个报文段，等了 100ms 仍没有收到 ACK，于是进行重传，又过了 20ms，发送方收到了 ACK ，但怎么区分这是来自最初发送的那个报文段（只不过可能反馈过程传输了很久），还是后来重传的那个？这叫作 **TCP 确认的二义性**，解决办法也很直接：不用这种有歧义的 ACK 去测量 SampleRTT

但是这样又出现了一个问题：如果网络真的变慢了，TCP 因为超时不断重传，又一直不更新 RTT，那么超时值可能始终偏小，导致反复重传

为了解决这个问题，就需要**定时器补偿（指数退避）**：发送方每重传一个报文段，就直接将超时值增大一倍（会设定上限），连续发生超时事件，超时值就会呈指数增长，这样当网络确实拥堵或延迟增大时，TCP 会逐渐延长等待时间，避免过于频繁地重传

**Karn算法**就是把两条原则结合起来
- 不对已经重传的数据包进行有歧义的 RTT 测量，如果持续超时，就使用指数退避增大超时值
- 等到有未重传的报文段得到正常确认，再用有效的 RTT 估计调整超时设置

### 快速重传

有时候，TCP 不必等到超时，就已经有很强的理由判断某个报文段丢失了，比如发送端发送了若干连续报文段，其中序号120～139 丢失，但后面的 140～159、160～179、180～199 都正常到达，接收方一直缺 120～139，所以每次收到后面的报文段，都无法推进累积 ACK，只能持续返回 `ACK=120` ，发送端收到连续的 `ACK=120` ，说明这段报文很可能丢失了，就不需要等到超时时间，立刻进行重传，这就是**快速重传（Fast Retransmit）**

### 延迟确认

前面一直假设接收方收到一个 TCP 报文段，就立刻返回一个 ACK，但如果发送方连续发送很多小报文段，接收方每次都立即发 ACK，网络中就会产生大量确认报文

TCP 使用**延迟确认（Delayed ACK）**：接收方可以在某些情况进行等待，看看能不能用一个 ACK 确认多个连续收到的报文段，但也不能等太久，否则可能误触发超时重传；而且也不能所有情况都等，比如发现接收的顺序是乱序的，就得及时反馈让发送方重传

| 接收方遇到的情况            | 处理方式          |
| ------------------- | ------------- |
| 按序收到一个报文段，之前没有待确认数据 | 可以暂时延迟确认      |
| 再收到一个按序报文段，前一个仍未确认  | 立即发送累积 ACK    |
| 收到乱序报文段，发现序号间隙      | 立即发送重复 ACK    |
| 收到的数据补上了之前的间隙       | 立即确认，并尽可能推进序号 |

### 选择确认 SACK

既然接收方可以缓存乱序数据，为什么不直接告诉发送方哪些后续字节已经收到了？这就引出了**选择确认（SACK，Selective Acknowledgment）**

假设接收方已经连续收到 0～99，并且提前收到了 200～299，但 100～199 缺失，普通的累积确认只能告诉发送方 `ACK=100` ，如果使用 SACK，接收方可以额外附带 SACK 选项，描述已经收到的非连续数据块的边界

发送方利用这些信息，就能够更准确地判断哪部分的数据已经到达、哪些数据仍然缺失，减少不必要的重传

## TCP 的连接管理

### TCP 报文结构

其中 RST、SYN、FIN 是 1bit 标志位，取值为 0/1 
- `SYN=1`：请求建立连接
- `FIN=1`：发送方不再发送数据
- `RST=1`：重置连接

### 建立连接：三次握手

正式传输数据之前，客户端和服务器需要先建立 TCP 连接，通过报文一步步协商，确保双方都愿意连接
- **第一次握手：客户端→服务端（SYN）**
	- 发送 `SYN=1, Seq=x` 
	- 表示“我想建立连接，我的起始序号是 x ”
	- 客户端进入 `SYN_SENT` 状态
- **第二次握手：服务端→客户端（SYN+ACK）**
	- 发送 `SYN=1, ACK=1, Seq=y, ACKnum=x+1` 
	- 表示“我也同意建立连接，我的起始序号是 y ，我确认了你的 SYN”
	- 服务器进入 `SYN_RCVD` 状态，并准备相关连接资源
- **第三次握手：客户端→服务端（ACK）**
	- 发送 `ACK=1, ACKnum=y+1` 
	- 表示“我也确认了你的 SYN”
	- 服务器收到这个确认后，便知道客户端收到了自己的回应，双方进入 `ESTABLISHED` 状态，可以正常传输数据

这里 ACK num 取 x+1、y+1，是因为双方的 SYN 占了一个序号位

为什么需要三次握手而不是两次？假设客户端发送建立连接的请求，但这个请求在网络里延迟了，客户端等不到回应，可能已经放弃这次连接，很久以后那个旧请求才到达服务器，如果服务器收到请求后直接认为连接已经建立，那么它可能为一个早已不存在的客户端保留连接状态

初始序号为什么不固定为 0 ？如果每次建立连接都从 0 开始，那么同一对 socket 之间，旧连接中延迟到达的报文就可能与新连接的序号重叠，接收方可能把旧数据误认为新数据

### 关闭连接：四次挥手

关闭连接相比建立时，有一个很重要的区别：TCP 是全双工的，两个方向都可能有数据传输，停止的条件是双方都没数据要发了
